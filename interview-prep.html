Blog Writing App — Interview Preparation

Complete Q&A guide + Project Summary  |  Prepared for: Keerthishree  |  Stack: Next.js · TypeScript · Prisma · Auth.js · Tailwind · Vercel

1. Project Introduction Questions

Tell me about your blog project.

I built a full-stack blog writing application from scratch using Next.js 16 with the App Router, TypeScript, Tailwind CSS, Prisma ORM with PostgreSQL (Neon), and Auth.js v5 for authentication. It supports Google OAuth and email/password login, rich-text editing with TipTap, tag filtering, author profiles, reading time estimates, like buttons, share functionality, related posts, a reading progress bar, and is fully responsive for mobile and desktop. It's deployed on Vercel.

Why did you choose this tech stack?

Next.js gives me both frontend and backend in one framework — server components reduce client-side JavaScript, and API routes handle the backend. TypeScript adds type safety which catches bugs early. Prisma gives a type-safe ORM so database queries are predictable. Tailwind speeds up UI development. Neon PostgreSQL is serverless and works perfectly with Vercel's serverless architecture.

What was the most challenging part of this project?

Setting up Auth.js v5 with the Next.js 16 App Router was the hardest part. The newer versions have breaking API changes — for example, the middleware in Next.js 16 requires a proxy pattern instead of the traditional middleware file. Also migrating from SQLite to PostgreSQL on Vercel required fixing the Prisma migration lock file provider from "sqlite" to "postgresql" and consolidating all migrations into PostgreSQL-compatible SQL.

2. Next.js & React Questions

What is the difference between Server Components and Client Components?

Server Components render on the server — they can directly access databases, secrets, and file systems, and they send zero JavaScript to the browser. Client Components use "use client" at the top and run in the browser — they can use hooks like useState, useEffect, and browser APIs. In my project, post pages are server components that fetch data from PostgreSQL directly, while the like button, mobile nav, and reading progress bar are client components because they need interactivity.

What is the App Router and how is it different from the Pages Router?

The App Router uses the app/ directory and enables React Server Components by default. It supports nested layouts via layout.tsx files, server-side data fetching inside components, and streaming with Suspense. The old Pages Router in the pages/ directory used getServerSideProps / getStaticProps for data fetching, which is more verbose and doesn't support React Server Components.

How does dynamic routing work in your app?

Dynamic routes use folder names with square brackets. For example, app/posts/[id]/page.tsx handles any URL like /posts/abc123. In Next.js 16, the params are a Promise, so I must await params before using them: const { id } = await params. I also have app/author/[name]/page.tsx for author profile pages.

What is the purpose of layout.tsx?

The layout.tsx wraps all pages at a given route level and persists across navigation — it doesn't re-render when the page changes. I use the root layout to render the sidebar, mobile nav, theme provider, and font. This means the sidebar is always visible without re-mounting on every page transition.

How did you implement dark mode?

I used the next-themes library with attribute="class", which adds a dark class to the <html> tag. In Tailwind CSS v4, the built-in dark variant uses a media query by default, so I overrode it with @custom-variant dark (&:where(.dark, .dark *)) in globals.css to make it class-based. Both <html> and <body> tags need suppressHydrationWarning to prevent hydration mismatch warnings.

How did you make the app responsive for mobile?

I used Tailwind's responsive prefixes. The desktop sidebar has hidden md:flex — hidden on mobile, shown as flex on medium screens and above. For mobile I built a MobileNav client component with a hamburger button that opens a slide-in drawer. It's shown with md:hidden. Main content padding adjusts with px-4 md:px-8.

3. Database & Prisma Questions

What is Prisma and why use it over raw SQL?

Prisma is a type-safe ORM (Object Relational Mapper). Instead of writing SQL strings, I write JavaScript/TypeScript like prisma.post.findMany(). The main benefit is type safety — the TypeScript types for my queries are auto-generated from the schema, so if I try to access a field that doesn't exist, I get a compile-time error. It also handles connection pooling, migrations, and works great with serverless environments via the @prisma/adapter-pg.

What does your database schema look like?

I have two models. Post has fields: id (cuid), title, content, tags (comma-separated string), authorId, authorName, likes (integer), createdAt, and updatedAt. User has: id, name, email, password (bcrypt hashed), and createdAt. I kept tags as a comma-separated string to keep the schema simple — a many-to-many tags table would be cleaner at scale but unnecessary for this project.

How do database migrations work in Prisma?

When I change the schema, I run npx prisma migrate dev --name description which creates a new SQL migration file in prisma/migrations/ and applies it. On Vercel deployment, the build script runs prisma migrate deploy which applies any pending migrations to the production database. There's also a migration_lock.toml file that locks the provider — it must say postgresql to match the schema.

How did you add the likes feature to the database?

I added a likes Int @default(0) field to the Post model, then created a new migration file with ALTER TABLE "Post" ADD COLUMN "likes" INTEGER NOT NULL DEFAULT 0. I also created an API route at /api/posts/[id]/like that uses Prisma's atomic increment: prisma.post.update({ data: { likes: { increment: 1 } } }) — this is safe under concurrent requests because it's a single atomic DB operation.

4. Authentication Questions

How did you implement authentication?

I used Auth.js v5 with two providers: Credentials (email + password) and Google OAuth. For credentials login, when a user registers I hash their password with bcrypt (cost factor 12) and store it. On login, I compare the input password against the hash with bcrypt.compare(). For Google OAuth, I set up a Web Application type OAuth client in Google Cloud Console with the correct redirect URIs. Sessions use the JWT strategy — no session table needed in the database.

What is the difference between auth.ts and auth.config.ts?

auth.ts is the full server-side config — it imports Prisma and bcrypt, handles the credentials provider logic, and is used everywhere except middleware. auth.config.ts is an Edge-safe config that has no Node.js-specific imports (no Prisma, no bcrypt) and is only used by the proxy/middleware because Next.js middleware runs on the Edge runtime which doesn't support all Node.js modules.

How did you protect routes like /posts/new?

In Next.js 16, instead of middleware.ts, I use a proxy.ts file that checks if the user is authenticated before allowing access to protected routes. If not authenticated, it redirects to the login page. Inside server components I call auth() directly to get the session, and in API routes I check the session and return 401 if the user isn't logged in.

How did you implement admin-only permissions?

I hardcoded the admin email keerthishreets@gmail.com as a constant. In the delete and edit API routes, I check: if the session user's email matches the admin email, allow the action regardless of who owns the post. Otherwise, only the original author can edit/delete their own post. This check exists in both the API route and the UI — the edit/delete buttons are only shown when isOwner = isAdmin || post.authorId === session.user.id.

Why use JWT strategy instead of database sessions?

JWT sessions are stateless — the session data is stored in an encrypted cookie on the client, so there's no need for a sessions table in the database. This is better for serverless deployments like Vercel where each request might hit a different server instance. The tradeoff is that you can't instantly invalidate a session (you'd have to wait for the token to expire), but for a blog app that's acceptable.

5. API & Backend Questions

How did you structure your API routes?

I followed REST conventions under app/api/posts/. The route.ts file handles GET (all posts) and POST (create). The [id]/route.ts handles GET (one post), PUT (update), and DELETE. There's also [id]/like/route.ts for the like increment. Each mutating route checks authentication first and returns a 401 if the user isn't logged in, and 403 if they're not authorized.

How does the like button work technically?

The LikeButton is a client component. When clicked, it calls POST /api/posts/[id]/like which atomically increments the likes count in PostgreSQL. To prevent double-liking, the browser stores liked post IDs in localStorage under liked_posts. On mount, it checks this list and disables the button if the post was already liked. This is per-browser, not per-user, so it's a soft prevention rather than a hard database constraint.

How did you implement reading time?

I created a lib/readingTime.ts utility. It strips all HTML tags from the content using a regex, splits the remaining text into words, and divides by 200 (average reading speed in words per minute). The result is rounded and has a minimum of 1 minute. It's used in both PostCard (list view) and the post detail page header.

How does the related posts feature work?

On the post detail page, after fetching the current post, I extract its tags into an array. Then I fetch all other posts from the database and filter them in JavaScript to find ones that share at least one tag with the current post. I limit the result to 3, sorted by most recent. This runs on the server so there's no extra client-side fetch. If the post has no tags or no matching posts exist, the section is hidden.

6. Frontend Features Questions

How does the reading progress bar work?

The ReadingProgressBar is a client component fixed at the top of the page. It listens to the scroll event with { passive: true } for performance. The progress percentage is calculated as (window.scrollY / (document.documentElement.scrollHeight - window.innerHeight)) * 100. The bar is a div with width: ${progress}% and a violet background. The event listener is cleaned up in the useEffect return function.

How does the share button work?

The ShareButton client component has three options. "Copy link" uses the Clipboard API: navigator.clipboard.writeText(url) and shows a "Copied!" confirmation for 2 seconds. "Post on X" opens Twitter's intent URL with the post title and URL pre-filled. On mobile, a native share button uses the Web Share API: navigator.share({ title, url }) which opens the OS share sheet. The post URL is constructed server-side using the host header.

How does tag filtering work?

The TagFilter is a client component that uses useSearchParams and useRouter. When a tag is clicked, it calls router.replace('/?tag=tagname'). The home page is a server component that reads the tag search param and filters the posts array before rendering. Clicking an active tag again clears the filter. This approach keeps filtering logic on the server and makes the URL shareable.

How does the TipTap rich text editor work?

TipTap is a headless rich-text editor built on ProseMirror. I load it with next/dynamic and ssr: false because it uses browser-only APIs. It saves the HTML content to localStorage every 1.5 seconds as an auto-save. The content is stored as HTML in the database. On the post view page, it's rendered with dangerouslySetInnerHTML and styled using Tailwind's prose typography plugin.

7. Deployment & DevOps Questions

How did you deploy the application?

I deployed to Vercel using the Vercel CLI with vercel --prod --yes --scope keerthishree-s-projects. The build command is prisma migrate deploy && next build — it applies any pending DB migrations first, then builds Next.js. The postinstall script runs prisma generate to regenerate the Prisma client from the schema. All environment variables (DATABASE_URL, AUTH_SECRET, Google OAuth credentials) are stored in Vercel's environment variable settings.

What is Neon PostgreSQL and why use it?

Neon is a serverless PostgreSQL provider. It's perfect for Vercel deployments because it scales to zero when not in use (no idle costs), supports connection pooling for serverless functions, and has a generous free tier. The connection string is stored as DATABASE_URL in environment variables. I use @prisma/adapter-pg which connects via the pg driver optimized for serverless.

How do you handle environment variables?

Sensitive values like database URLs, API keys, and auth secrets never go in the code. They're stored in a .env file locally (gitignored) and in Vercel's dashboard for production. In Next.js, variables prefixed with NEXT_PUBLIC_ are exposed to the browser; everything else stays server-side only. The AUTH_SECRET is used by Auth.js to encrypt JWT tokens.

8. General & Conceptual Questions

What is MCP and how are you using it?

MCP stands for Model Context Protocol — an open standard by Anthropic that lets AI assistants connect to external tools and data sources. I've connected Google Custom Search MCP to Claude Code so that when I'm developing, the AI can search the web in real time for up-to-date documentation and answers instead of relying only on its training data.

How would you scale this app if it had millions of users?

Several things: add full-text search with PostgreSQL's tsvector instead of filtering in JavaScript; add a Redis cache layer for frequently-read posts; store images in S3/Cloudinary instead of the DB; add pagination for the posts list; move the like button to a proper per-user system with a separate Likes table; add a CDN for static assets; and consider using ISR (Incremental Static Regeneration) in Next.js to cache post pages at the CDN level.

What security measures did you implement?

Passwords are hashed with bcrypt at cost factor 12 — never stored in plain text. API routes check authentication before any mutation. Admin actions verify the user's email server-side. Prisma uses parameterized queries automatically so SQL injection is not possible. Environment variables keep secrets out of the codebase. The Auth.js AUTH_SECRET encrypts all JWT tokens. Route protection via the proxy prevents unauthenticated access to the editor.

What would you improve or add next?

I would add: a comment system so readers can engage with posts; draft/publish toggle so authors can save without making posts public; a cover image upload feature using Cloudinary; full-text search with PostgreSQL; email notifications when someone likes your post; and an RSS feed at /feed.xml for readers to subscribe via RSS readers.

Authentication

Email/password with bcrypt hashing + Google OAuth. JWT sessions. Route protection via proxy.

Rich Text Editor

TipTap editor loaded dynamically. Auto-saves to localStorage every 1.5s. Renders HTML with Tailwind prose.

Responsive Design

Desktop sidebar + mobile hamburger nav with slide-in drawer. Works on all screen sizes.

Dark Mode

Class-based dark mode via next-themes. Custom Tailwind v4 variant overrides media query default.

Tag Filter System

URL-param based filtering (?tag=). Server-side filtering. Shareable filtered URLs.

Author Profiles

Dynamic /author/[name] pages. Shows author's post count and all their posts.

Reading Progress Bar

Fixed violet bar at top. Scroll-event driven. Passive listener for performance.

Like Button

Atomic DB increment. localStorage deduplication. Like count shown on cards.

Reading Time

Share Button

Copy link + Post on X + native Web Share API on mobile. Clipboard API feedback.

Related Posts

Tag-based matching. Server-side. Shows up to 3 posts with overlapping tags.

Scroll Inspiration Banner

Random writing quote shown once per page visit on first downward scroll. 3s fade out.
